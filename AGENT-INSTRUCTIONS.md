CREATE TABLE credentials (
  id              TEXT PRIMARY KEY,
  key             TEXT NOT NULL UNIQUE,

### Story 2.3 — SSE infrastructure

**Branch:** `feature/phase2-sse-infrastructure`

See PLAN.md §6.9. Implement both SSE endpoints:

**`GET /api/threads/:id/stream`** — per-thread stream
- Emits `token` events (streaming LLM output)
- Emits `message_complete` event when the full response is persisted
- Emits `error` events with typed codes (e.g. `PROVIDER_UNAVAILABLE`)

**`GET /api/events`** — global stream
- Emits `thread_updated` events (new message, title change)
- Emits `routine_fired` events
- Emits `provider_status` events

Use Axum's SSE support (`axum::response::Sse`). Use `tokio::sync::broadcast` channels for the global stream — the `AppState` should hold a `broadcast::Sender<GlobalEvent>`. Per-thread streams use a `tokio::sync::mpsc` channel created per-connection.

Both streams must emit a `ping` event every 30 seconds to keep connections alive.

**Acceptance criteria (from PLAN.md):**
- Both SSE endpoints connect without error
- Token events stream correctly during a (mocked) LLM response
- Global stream receives events from other parts of the system
- 30-second keepalive pings work
- Disconnecting a client does not cause a panic or channel leak

### Story 2.5 — Agent run-loop with streaming ⚠️ Human review required

**Branch:** `feature/phase2-agent-run-loop`

Implement the agent run-loop in `server/src/services/agent.rs`. This is the core execution path for all chat interactions.

When `POST /api/threads/:id/messages` is called:
1. Persist the user message to DB with `visibility: visible`
2. Spawn a Tokio task to run the agent asynchronously
3. Return the persisted user message immediately (HTTP response)

The spawned task:
1. Calls `ContextAssembler` to build the request
2. Calls the active provider's streaming completion method
3. Streams tokens to the per-thread SSE channel as `token` events
4. On tool call (save_memory / recall_memory): execute the tool, append tool result to context, continue generation
5. Persists the complete assistant message to DB with `visibility: visible` when done
6. Emits `message_complete` SSE event
7. Emits `thread_updated` global SSE event (for sidebar refresh)

**Error handling:**
- If provider is unavailable: persist no assistant message, emit `error` SSE event with code `PROVIDER_UNAVAILABLE`
- If generation fails mid-stream: emit `error` event, do not persist partial message

**⚠️ This story requires human review before merging.** The async coordination between HTTP handler, SSE stream, and tool execution is subtle. Demonstrate end-to-end with a real LLM call before marking complete.

**Acceptance criteria (from PLAN.md):**
- User message returned immediately from POST
- Tokens stream to SSE client in real time
- Complete assistant message persisted after streaming finishes
- `save_memory` and `recall_memory` tool calls are handled inline
- Provider unavailable error surfaces via SSE, not HTTP error
- Integration test: send a message, verify SSE stream, verify DB state

4. **SQLx offline mode.** After any schema change, run `cargo sqlx prepare` and commit the updated `.sqlx/` directory. Set `SQLX_OFFLINE=true` for CI builds.
5. **Never expose `encrypted_data` in API responses.** The `credentials` table contains encrypted secrets. The `Credential` model (non-internal struct) must never include `encrypted_data`. This is a hard security rule.
6. **Hidden messages stay hidden.** The `GET /api/threads/:id/messages` endpoint filters out `visibility: hidden` messages by default. Only include them when `?include_hidden=true` is passed (for debugging).
7. **Mockups are the visual reference.** For every UI story, open the corresponding mockup file in `mockups/` and match it. Note: some mockups predate v1.4 and show a Skills section — ignore that section and implement the MCP section instead per PLAN.md §8.3.
8. **Stories 2.5 and 2.6 require human review.** Do not merge these without the human reviewing the actual running behavior.
